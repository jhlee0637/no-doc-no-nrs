# 타 오케스트라이제이션 플랫폼의 기능을 Codex로 재현

이 Skill의 목표는 타 오케스트라이제이션 플랫폼의 핵심 오케스트라이제이션 기능을 Codex 기본 Subagent·관련 Skill·작은 로컬 실행기로 재현하는 것이다. 작업 기록 → 담당자 지정 → 실행 → 결과·리뷰 → 완료 또는 인계의 한 운영 루프를 제공한다. 외부 플랫폼의 코드·서버를 실행하거나 Codex의 생성·메시징 엔진을 중복 구현하지 않는다.

## 재현 범위

| 가져오는 개념 | 이 Skill의 구현 수단 |
| --- | --- |
| 작업 큐와 담당자 | 기본 모드는 메인 원장; 영속 모드는 SQLite 큐·원자적 claim·시도 번호·이벤트 이력 |
| 역할별 위임과 메시지 | Codex 기본 Subagent 도구와 역할에 맞는 Skill 선택·전달 |
| 결과 취합과 리뷰 | 전문 Skill을 적용한 검토, 실제 검증 증거, 제한된 수정 루프 |
| 컨텍스트 인계 | 결정·현재 상태·다음 행동 기록과 실제 상태 대조; 기록된 Codex 세션의 명시적 resume |
| 타이머·watchdog | 실행 중인 감시기의 기한·heartbeat 만료 감지, 중복 억제된 알림 |
| 자동 깨우기 | 명시적으로 승인한 감시 실행에서만 제한된 codex exec 또는 지정 세션 resume |

`SKILL.md`만으로 프로세스가 시작되지는 않는다. 영속 저장·감시는 `scripts/orchestrate.py`가 담당한다. 감시기가 종료되거나 컴퓨터가 꺼지면 깨우기도 멈춘다. 기존 채팅/TUI에 메시지를 주입하거나 메모리·프로세스 스냅샷을 복원하지 않는다. 기록된 네이티브 대화를 새 Codex 프로세스로 재개하는 것과 런타임 복원은 다르다. 기존 GitHub 협업 Skill은 수정·연결·실행하지 않는다.

## 실행 모드 선택

- 단발성·현재 채팅의 협업은 아래 기본 Subagent 루프를 사용한다. Markdown 원장은 수동 인계 기록이며 실행 큐가 아니다.
- 영속 큐·예약·감시·실행 중단 후 재개를 요청받으면 [로컬 실행기 규약](references/ai-generated-local-runtime.md)을 **끝까지 읽은 뒤** `scripts/orchestrate.py`를 사용한다. SQLite가 상태의 유일한 원본이며 Markdown 사본을 별도 갱신하지 않는다.
- 큐 등록·알림만으로 AI 실행은 승인되지 않는다. 기본 감시는 알림만 기록·출력한다. 자동 실행에는 사용자와 대상 작업·workspace·검토한 Codex profile·sandbox·기간·호출 상한을 합의하고 `--dispatch-codex --authorize-exec`를 명시한다.
- 실행기 개발·테스트 요청은 장시간 감시·서비스 등록·유료 Codex 호출 승인이 아니다. 설치·인증·전역 설정·OS 스케줄러 변경은 별도 합의한다.

## 시작과 권한

- 사용자의 현재 목표, 변경 또는 검토 권한, 완료 조건, 실행 예산을 확인한다. 토의·계획이면 분해안만 제안하고 작업을 실행하지 않는다.
- 현재 세션에 제공된 Codex Subagent 도구를 확인한다. 없으면 메인이 동일한 기록·검증 절차로 순차 수행한다. 존재하지 않는 명령이나 별도 런타임을 만들지 않는다.
- 부모의 모델·권한·샌드박스 설정을 기본적으로 유지한다. 외부 API나 다른 에이전트 런타임으로 대체하지 않는다.
- 이 Skill은 승인 범위를 넓히지 않는다. GitHub 게시, 커밋·푸시·병합, 권한·설정 변경은 별도 사용자 요청이나 명시적 운영 합의가 필요하다.

## Codex Subagent 관련 Skill 사용법

### 역할·도구·Skill을 구분한다

- 이 Skill은 메인의 작업 배정·상태·완료 판단을 담당한다.
- Subagent 도구는 실제 에이전트를 생성하고 지시·결과를 전달한다. Skill 이름을 언급하거나 파일을 읽는 것만으로 에이전트가 생성되지는 않는다.
- Skill은 각 역할이 수행할 작업 절차다. `worker`·`explorer` 같은 기본 에이전트 역할은 Skill 이름이 아니다. 해당 역할 선택 기능이 현재 도구에 없으면 제공된 기본 에이전트에 역할을 지시한다.
- Subagent 관련 Skill이 별도로 없더라도 기본 도구로 위임할 수 있다. 없는 Skill을 설치하거나 만들어야만 실행할 수 있다고 판단하지 않는다.

### 필요한 Skill만 발견하고 읽는다

1. 현재 세션의 Skill 목록과 프로젝트 지침에서 작업과 관련된 이름·설명·접근 위치를 확인한다. 후보가 명시되지 않았다면 실제로 읽을 수 있는 로컬 Skill 목록을 확인한다. 파일 존재와 현재 세션의 자동 등록 상태는 구분한다.
2. 메인이 선택한 Skill의 `SKILL.md`를 끝까지 읽고, 해당 작업에 필요한 연결 지침도 읽는다. 지침 해석을 Subagent에 통째로 맡기지 않는다. 관련 없는 Skill을 모두 읽거나 삭제한 초안 이름을 의존성으로 사용하지 않는다.
3. 선택한 Skill의 수정·네트워크·모델·재위임 조건이 이번 권한과 맞는지 확인한다. 권한을 확장해야만 쓸 수 있으면 필요한 결정을 요청하거나 기본 절차로 수행한다.
4. 위임할 때 확인한 Skill 이름과 이번 환경에서 접근 가능한 위치, 읽을 지침, 역할·산출물 범위를 전달한다. 다른 컴퓨터에도 같은 설치 경로가 있다고 가정하지 않는다.
5. Subagent도 실제 작업 전에 지정된 Skill과 필요한 참조를 직접 읽게 한다. 접근할 수 없으면 실패 사실을 회신하고 메인이 대체 절차를 결정한다. Skill 적용 여부와 미적용 이유를 결과에 기록한다.

| 역할·단계 | Skill 적용 기준 |
| --- | --- |
| 메인 조정 | 이 `codex-orchestration` Skill로 작업 원장·배정·결과 취합·인계 관리 |
| 탐색 담당 | 제공된 탐색 역할과 읽기 중심 지시 사용; 관련 탐색 Skill이 실제로 있을 때만 적용 |
| 구현 담당 | 작업 분야에 맞는 구현·테스트 Skill이 있으면 선택; 없으면 파일 범위·완료 조건을 지정해 기본 Worker로 수행 |
| 코드 Reviewer | `review-agent`가 목록에 있거나 실제 지침을 확인할 수 있으면 사용; 읽기 전용·결함 중심 검토 결과를 받음 |
| 비코드 검토 또는 리뷰 Skill 없음 | `review-agent`를 억지로 적용하지 않고 명시적 검토 기준으로 수행; 독립 Subagent가 없으면 메인이 검토했다고 표시 |

`review-agent`는 선택적 연계 예시이지 필수 설치 의존성이 아니다. 적용 시 실제 코드 변경과 검토 기준 diff를 지정하고 파일 수정·커밋·외부 게시·재위임을 허용하지 않는다. 실행 테스트가 필요하면 구현 담당자가 허용 범위에서 수행한다. 리뷰 Skill의 `No findings.` 결과도 완료 조건별 검증을 대신하지 않는다.

### 위임과 피드백에 Skill을 연결한다

위임 메시지는 다음 항목을 포함한다. Skill 위치는 실행 환경에서 확인한 값이며 공개 문서에 개인화된 절대 경로를 복사하지 않는다.

```text
task_id / attempt / role:
goal / excluded_scope:
selected_skills: 실제 확인한 이름·접근 위치, 없으면 없음
skill_reading: 해당 SKILL.md와 필요한 참조를 직접 읽은 뒤 작업
inputs / contract_or_diff_base:
owned_paths / forbidden_paths:
acceptance / allowed_verification:
return: 작업 ID·시도, 적용 Skill, 산출물, 실제 검증, 미검증·차단 항목
```

역할을 배정한 뒤 Skill의 실행 방식과 현재 제공된 도구로 작업한다. 추가 설명은 메시지 도구로, 쉬고 있는 담당자에게 새 작업이나 수정 요청은 실제 후속 작업·재개 도구로 전달한다. 도구 이름·인자는 현재 환경의 정의를 따르며 존재하지 않는 공통 CLI 명령을 만들지 않는다.

Worker 결과 → 메인의 산출물 확인 → Reviewer의 검토 → 메인의 수정 필요성 판단 → 같은 구현 담당자의 수정 → 재검증 순으로 연결한다. Reviewer가 보고한 항목을 사용자 승인으로 취급하지 않으며, Skill 간 위임을 반복하여 중첩 에이전트나 무한 리뷰 루프를 만들지 않는다.

## 1. 작업을 기록하고 담당자를 정한다

기존 작업 원장이 있으면 재사용한다. 사용자가 구현·상태 보존을 요청했는데 원장이 없으면 프로젝트 상대 경로 `docs/ai-generated-orchestration-state.md`를 기본 후보로 사용한다. 기존 파일과 관련 지침을 읽고, 충돌하거나 다른 위치를 지정받았으면 그 위치를 따른다. 개인 경로·API 키·세션 UUID를 기록하지 않는다.

메인 한 명만 원장을 수정한다. Worker는 원장에 직접 쓰지 않고 결과를 회신한다. 영속 모드에서는 메인 또는 승인된 실행기가 CLI를 통해 큐를 수정하며 Worker가 DB를 직접 편집하지 않는다. 두 컴퓨터는 SQLite 파일을 동기화·공유하지 않고 각각 로컬 큐를 사용한다. 원장 담당자를 바꾸려면 이전 담당자의 쓰기 종료를 확인한다.

각 작업은 아래 정보만큼 구체적으로 기록한다.

```text
작업 ID / 목표 / 제외 범위:
담당 역할 / 상태 / 현재 시도 번호:
선행 작업 ID / 입력 자료·계약 버전:
선택한 Skill 이름 / 적용 여부·미적용 이유:
수정 가능한 프로젝트 상대 경로 / 공통 파일 담당자:
완료 조건 / 허용된 검증 방법:
결과물 경로 / 실제 검증 결과 / 남은 위험:
차단 사유·해제 조건 / 다음 행동:
상태 변경 시각·이유 / 담당자 변경 이력:
```

담당자는 한 작업에 한 명이다. 서로 다른 Worker의 수정 경로는 겹치지 않게 한다. 공통 타입·설정·manifest·lockfile은 메인 또는 지정된 통합 담당자가 소유한다. 선행 결과가 필요한 작업은 `queued`로 두며, 선행 결과 없이 시작 가능한 작업만 병렬화한다.

## 2. 배정하고 실제로 실행한다

- 단순하거나 직렬인 작업은 메인이 직접 수행한다. 병렬 작업은 메인 + Worker 최대 2명으로 시작하고, 실제 세션 한도·사용자 예산이 더 작으면 그 한도를 따른다. Worker의 재위임은 기본적으로 금지한다.
- 위임 메시지에 작업 ID·시도 번호, 목표, 선택한 Skill·읽을 입력, 수정 경로, 금지 범위, 완료 조건, 검증 방법과 중간 보고 조건을 포함한다.
- Subagent 생성 성공과 실제 담당자를 확인한 뒤 `active`로 기록한다. 생성 실패를 실행 중으로 표시하지 말고 실패 원인에 따라 메인 수행 또는 `blocked`로 정리한다.
- Worker는 결과를 기존 메시지 도구로 메인에게 반환한다. 메인은 독립 작업을 계속하며 필요한 시점에 상태나 결과를 확인한다.
- 대기 중인 에이전트에게 단순 메시지를 보냈다고 실행이 재개된다고 추정하지 않는다. 현재 환경의 후속 작업·재개 도구가 필요하면 그 도구를 사용하고 결과를 확인한다.
- 영속 모드의 실제 claim·heartbeat·결과 제출은 실행기 규약을 따른다. 현재 채팅의 Subagent를 배정하는 경우에도 메인이 claim 정보를 보유하고 회신의 작업 ID·시도를 확인한 뒤 결과를 제출한다. CLI 실행기는 같은/상하위 workspace의 active 작업을 보수적으로 직렬화하므로 병렬 큐 작업은 분리된 worktree 또는 작업 폴더를 사용한다.
- 영속 모드의 `active`는 claim을 통한 독점권 예약부터 시작한다. 실제 실행 여부는 `launched` 이벤트·프로세스 또는 Subagent 생성 성공을 별도로 확인한다. `active` 기록만으로 에이전트가 실행됐다고 주장하지 않는다.

## 3. 결과를 받아 리뷰·수정한다

결과에는 작업 ID·시도 번호, 적용 Skill과 미적용 이유, 변경 파일, 완료 조건별 증거, 실제 테스트 명령·결과, 미검증 항목, 차단 문제를 포함한다. 메인은 원장과 실제 산출물을 비교한다. 이전 시도의 늦은 응답이나 다른 작업의 결과를 현재 완료로 적용하지 않는다.

구현 결과는 `review`로 옮기고, 위임이 가능하면 구현자와 다른 Reviewer 한 명에게 읽기 전용 검토를 요청한다. 앞의 Skill 선택 절차에 따라 코드 리뷰에는 사용 가능한 `review-agent`를 적용한다. Reviewer의 원본 발견 사항과 검토 한계를 보존하고, 메인이 산출물·diff·검증 증거를 대조하여 `검토 범위 내 문제 없음`, `수정 필요`, `증거 부족`으로 정리한다. 메인이 검토했다면 독립 리뷰를 받았다고 쓰지 않는다.

- 리뷰만 요청받았으면 발견 사항 보고에서 끝낸다. 수정 권한 없이 `rework`를 실행하지 않는다.
- 수정 필요 시 항목과 재현 근거를 기존 구현 담당자에게 전달한다. 코드 수정 전 Reviewer의 읽기 전용 역할과 구현자의 쓰기 소유권을 명확히 한다.
- 첫 구현 이후 수정·재검증은 최대 2회다. 동일 장애가 반복되거나 예산·권한이 부족하면 조기에 멈추고 남은 문제를 보고한다. 새 에이전트 생성이나 시도 번호 초기화로 한도를 우회하지 않는다.
- 코드가 작성됐다는 이유만으로 `done` 처리하지 않는다. 합의된 완료 조건과 필요한 실제 검증 증거가 있어야 한다. 검증 불가능은 통과가 아니라 `blocked` 또는 미완료다.
- 영속 모드에서도 Codex 종료 코드 0·turn.completed·결과 텍스트는 `review` 진입 증거일 뿐이다. 메인이 실제 산출물·테스트·독립 리뷰를 확인하고 `accept --evidence-file`로 완료한다. Reviewer가 없으면 그 한계를 기록한다. 실행 성공을 품질 검증으로 바꾸지 않는다.

## 상태 전환

| 상태 | 다음 상태와 조건 |
| --- | --- |
| `queued` | 선행 작업 완료·담당자 확인·실행 착수 후 `active` |
| `active` | 결과 제출 후 `review`; 장애·권한 부족 시 `blocked` |
| `review` | 완료 조건 충족 시 `done`; 허용된 수정 필요 시 `rework`; 증거 부족 시 `blocked` |
| `rework` | 수정 완료 후 `review`; 반복 한도·권한·예산 초과 시 `blocked` |
| `blocked` | 원인 해소와 담당자 확인 후 이전 진행 상태로 복귀; 실행 전이면 `queued` |
| `done` | 종료 상태. 새로운 범위는 새 작업 ID로 기록 |
| `cancelled` | 종료 상태. 실제 담당자의 중단 확인을 기록 |

`blocked`에는 차단 사유, 이전 상태, 해제 조건, 다음 판단 담당자를 기록한다. 실행 중 작업을 재배정하기 전에 기존 Worker의 종료·쓰기 중단을 확인하고 시도 번호를 증가시킨다. 무응답만으로 중단됐다고 추정하거나 동일 작업을 중복 실행하지 않는다.

영속 실행기의 저장 상태는 `queued/active/review/blocked/done/cancelled`다. `rework`는 리뷰 결과·수정 사유를 이력에 보존하고 시도와 수정 횟수를 증가시켜 `queued`로 되돌리는 명령이다. 수정 담당자·workspace·원래 세션은 유지하며 수정 횟수는 최대 2회다. 기본 모드의 개념적 `rework` 상태와 이 저장 표현을 혼동하지 않는다.

## 4. 상태를 인계하고 재개한다

인계 시 전체 대화 대신 사용자 목표·승인 범위, 확정/미확정 결정, 작업별 상태·담당자·시도·적용 Skill, 결과물·검증 증거, 현재 Git 기준·미커밋 변경, 차단 사항과 첫 다음 행동을 원장에 남긴다. 실제 실행 식별자는 공개 기록에 복사하지 않는다. 재개 환경에서는 관련 Skill의 존재·내용·권한을 다시 확인한다.

다음 에이전트는 원장부터 읽고 현재 브랜치·파일·산출물과 대조한다. 이전 `active`·`rework` 작업의 실행 상태를 확인할 수 없으면 복원됐다고 가정하지 말고 확인 필요로 표시한다. 관련 완료 조건이 바뀌었거나 산출물이 없으면 이전 `done` 기록과 현재 유효성의 차이를 보고한다.

영속 모드에서는 같은 비공개 DB의 `recover/status/events`부터 확인한다. lease 만료는 정체 신호이지 작업자 종료 증거가 아니다. 기존 프로세스·자식 작업자의 쓰기 종료를 실제 확인한 뒤에만 `requeue --writer-stopped`를 사용한다. 실행기가 기록한 네이티브 세션 ID가 있을 때만 `--resume`으로 해당 세션을 재개하며 `--last`·자동 새 세션 대체·설정 완화는 사용하지 않는다. Subagent ID는 CLI resume 대상이 아니다. 세션 파일·profile·인증이 없는 다른 컴퓨터에서는 자동 복원을 주장하지 않는다.

원장이나 산출물을 읽는 것만으로 재실행·외부 게시가 승인되지는 않는다. 현 사용자 요청과 권한 안에서만 재개한다. 중단 요청을 받으면 이 루프가 생성한 Worker의 실제 중단 상태를 확인하고 마지막 결과를 기록한다. 관계없는 세션이나 프로세스는 종료하지 않는다.

## 종료 보고

완료·대기·차단·취소 작업, 실제 검증, 남은 위험, 원장 위치와 다음 행동을 짧게 보고한다. 모든 요청 작업의 완료 조건이 충족되기 전에는 전체 완료를 주장하지 않는다. 영속 모드에서는 큐 상태와 실행 결과를 대조하고 감시기의 실제 생존·기간·호출 횟수도 보고한다. 알림 이벤트 저장·stdout 출력은 수신 ACK나 작업 완료가 아니다. 원본 로그·개인 경로·실행 식별자는 비공개 상태 디렉터리에만 보관한다.

Codex 기능·구성의 공식 근거: [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Build skills](https://learn.chatgpt.com/docs/build-skills), [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode). 타 오케스트라이제이션 플랫폼 전체와 동일한 런타임·자동 복구를 제공한다는 뜻은 아니다.
